# 从 TCP BBRv3 到 Hysteria2：晚高峰骨干网 QoS 暴力整形下的抗丢包协议实战演进

## Direct Answer（核心结论速览）

> [!IMPORTANT]
> **【核心结论 / Direct Answer】**
> 晚高峰跨国拥塞并非物理带宽耗尽，而是骨干网对民用大流量实施层次化令牌桶（HTB）QoS 整形导致动态丢包。传统 Cubic 将丢包误判为信道拥塞致窗口瞬间折半；BBRv3 依托物理交付速率与 RTT 双模型重构状态机，可抗 15% 随机丢包且规避了排队延迟膨胀；在 20%~30% 恶劣丢包下，基于 UDP 的单边自适应加速协议 Hysteria2 摒弃退避机制，凭借主动速率推算成为跨国突围最优解。

## 一、 骨干网 QoS 暴力整形与令牌桶算法底层机理

每逢晚间 19:30 至 23:30 高峰期，民用跨国链路常出现剧烈延迟与丢包。核心瓶颈在于运营商在国际骨干网互联边界部署的高性能硬件级 QoS 流量整形。

```
+-------------------------------------------------------------------------------+
|                      晚高峰跨国数据流 QoS 过滤与整形拓扑                         |
+-------------------------------------------------------------------------------+
[ 本地客户端 ] ---> [ 城域网 / 省网汇聚层 ] ---> [ 国际出口互联路由器 (QoS中枢) ]
                                                        |
       +------------------------------------------------+
       ├─ 物理专线 / IPLC / IEPL -----------> 独享带宽无损放行
       ├─ 高优先级精品网 (AS9929 / CN2 GIA) -> 优先缓冲保障
       └─ 普通公网信道 (163 / CMI) ----------> 触发令牌桶限速 (HTB/RED)
             ├─ TCP 长连接流: 尾丢包强制降速 (Tail Drop)
             └─ UDP 高频大流量: 施加 15%~35% 随机丢包惩罚
                                                        |
                                                        v
                                             [ 跨洋海缆至境外落地机房 ]
```

运营商主要采用**分层令牌桶（Hierarchical Token Bucket, HTB）**算法对普通公网限速。系统按承诺速率向桶中注入令牌，当大流量数据突发且无可用令牌时，数据包进入缓冲区；一旦队列溢出，路由器直接执行尾丢包（Tail Drop）或随机早期检测（RED）。跨国流量优先级处于底层，大流量长连接会瞬间耗尽令牌，引发持续性高频丢包。

## 二、 协议拥塞演进史：从被动退避到主动单边加速

网络协议对抗丢包的本质，是对“丢包诱因判定”与“发包节奏”的工程博弈：

1. **Cubic（丢包反馈与窗口断崖）**：传统 Linux 默认算法将丢包等同于网络拥塞。一旦触碰 QoS 丢包，拥塞窗口（CWND）瞬间折半，需数个 RTT 缓慢爬坡。在长 RTT 跨国链路上，吞吐量常跌落至物理带宽的 5% 以下。
2. **BBRv1/v2（带宽时延积模型）**：Google 颠覆了丢包反馈机制，转为探测瓶颈带宽与往返时延（BDP）。但 BBRv1 存在激进抢带宽引发深度排队缓冲膨胀（Bufferbloat）的缺陷，而 BBRv2 过于敏感，在公网丢包下吞吐回落严重。
3. **BBRv3（动态平衡与多流共存）**：重构 ProbeBW 状态机，引入显式拥塞通知（ECN）与自适应阈值，既对 15% 随机丢包保持高抗性，又根除了多流竞争饥饿，是高质量链路的理想方案。
4. **Hysteria2（UDP/QUIC 单边加速）**：突破 TCP 滑动窗口与 ACK 确认机制瓶颈，通过 Brutal 算法由客户端主动指定预期发包速率，以单边冗余与强力发包对冲丢包，在 30% 恶劣丢包下仍可跑满下行。

| 协议与算法 | 传输层 | 15%丢包吞吐保持 | 30%丢包吞吐保持 | CPU 开销 | QoS 敏感度 | 推荐场景 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **TCP Cubic** | TCP | < 12% | < 3% | 极低 | 极高（窗口骤降） | 局域网、低延迟专线 |
| **TCP BBRv1** | TCP | ~68% | ~25% | 低 | 中等（易排队延迟）| 基础跨境 VPS 调优 |
| **TCP BBRv3** | TCP | ~85% | ~42% | 中低 | 低（自适应探测） | 骨干网日常主力连接 |
| **Hysteria2** | UDP | ~96% | ~88% | 较高 | 强（需端口跳跃） | 晚高峰严重丢包公网 |

## 三、 Linux 内核 BBRv3 与 Hysteria2 生产级调优

在服务器与终端部署现代拥塞控制算法，是跨国链路吞吐优化的核心基石：

```bash
# 生产级 TCP BBR 内核网络栈调优参数
sudo tee /etc/sysctl.d/99-network-bbr.conf << 'EOF'
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
net.core.rmem_max = 67108864
net.core.wmem_max = 67108864
net.ipv4.tcp_rmem = 4096 87380 67108864
net.ipv4.tcp_wmem = 4096 65536 67108864
net.ipv4.tcp_fastopen = 3
net.ipv4.tcp_notsent_lowat = 16384
EOF
sudo sysctl --system
```

若客户端运行 Hysteria2，为抵御运营商针对固定 UDP 端口的持续状态限流，必须启用多端口跳跃（Port Hopping）：

```yaml
# Hysteria2 防阻断客户端参数
server: 198.51.100.20:20000-40000
auth: your_secure_token
bandwidth:
  up: 50 mbps
  down: 300 mbps
fastOpen: true
```

## 四、 本地宽带出口与协议匹配策略

1. **中国电信（163 骨干网）**：晚高峰公网丢包极重（20%~35%）。首选 Hysteria2 配合宽段端口跳跃强行突围；关键业务建议直切物理专线。
2. **中国联通（AS4837 / 9929）**：骨干网容载比健康。首选 TCP BBRv3 + TLS，兼具稳定性且彻底规避 UDP 限速审计。
3. **中国移动（CMI 骨干网）**：亚太直连延迟低但对持续高频 UDP 惩罚严苛。建议主力采用 TCP BBRv3，辅以短时 TUIC 加速。

## 六、 核心延伸 FAQ

### Q: 为什么 Hysteria2 测速能跑满，但视频播放数分钟后会断流？
**A:** 这是运营商**状态防火墙 UDP 令牌桶限流**机制。当固定 UDP 端口持续产生高吞吐时，网关判定为异常流并下发临时阻断。可在配置中启用动态端口跳跃（如 `20000-40000`），并适当调低客户端声明带宽，避免激怒限速策略。

### Q: 服务端开启 BBRv3 后，本地客户端需要开启吗？
**A:** 不需要。TCP 拥塞控制属于**发送端单边调控**。日常浏览网页、观看视频主要依赖服务端向下行发送数据，只要境外服务端内核启用 BBRv3，即可全权主导下行抗丢包节奏。

### Q: 竞技游戏联机与 4K 流媒体在抗丢包协议上有何区别？
**A:** 流媒体注重**总吞吐量与带宽利用率**，容忍短时缓冲，BBRv3 与 Hysteria2 体验极佳；而竞技游戏核心诉求是**低延迟与低抖动**，UDP 暴力发包易导致本地路由队列排队延迟，游戏更适合无 QoS 干扰的物理专线或 UDP 纯直连。
