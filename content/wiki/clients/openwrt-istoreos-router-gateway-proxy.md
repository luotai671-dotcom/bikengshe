## 一、主路由与旁路由（透明网关）拓扑本质：全屋接管与单机客户端的根本差异

单机客户端（如 Windows / macOS 上的 Clash Verge、Sing-box）仅能在单个操作系统用户态或通过 TUN 虚拟网卡接管本机流量。面对不支持安装客户端的主机、电视盒子及移动端设备，必须将网络代理的能力下沉至局域网第 3 层（网络层）。

```
【传统单臂旁路由拓扑数据流向】
终端设备 (192.168.1.100) 
   │ [Default Gateway: 192.168.1.2]
   ▼
旁路由网关 (192.168.1.2 / iStoreOS) ──(Tproxy/TUN分流内核判别)
   ├─► 国内直连流量 ──► 物理主路由 (192.168.1.1) ──► 光猫 PPPoE ──► 国内运营商骨干网
   └─► 跨境加速流量 ──► 节点加密隧道 (AES/ChaCha20) ──► 物理主路由 ──► 境外服务器
```

1. **物理主路由一体化方案**：软路由作为核心网关直接负责光猫 PPPoE 拨号、DHCP 地址池分配以及 NAT 转换。该模式链路最短、网络跳数（Hop）最少，但对软路由硬件稳定性要求极高，一旦代理内核崩溃或配置错误，全屋网络将直接彻底瘫痪。
2. **旁路由（透明网关 / Bypass Gateway）方案**：主路由保留原有的稳定拨号与局域网 DHCP 分配功能，旁路由以局域网普通客户端身份接入。通过手动指定特定终端设备的默认网关（Gateway）和 DNS 为旁路由 IP，实现按需透明接管。这种架构具备极强的“容灾逃生能力”，但在配置不当时极易引发二层 ARP 广播风暴与四层 SYN 握手不对称路由问题。

## 二、软路由硬件算力与节点协议加密损耗深度横评

全屋网关加速并非单纯依赖宽带物理带宽，软路由 CPU 的单核整数运算性能与硬件指令集扩展，直接决定了加密流量吞吐量的物理上限。

1. **AES-NI 硬件指令集开销**：传统基于 TLS 握手的节点协议（如 VLESS-Reality、Trojan）使用 AES-128-GCM 或 AES-256-GCM 对称加密。具备 AES-NI 指令集的 X86 工控机（如 Intel N100、J4125）能够以极低的 CPU 占用跑满千兆吞吐；而缺少硬件指令集的老旧 ARM 架构或低功耗软路由，在面对大并发数据吞吐时 CPU 占有率将瞬间达到 100%，引发严重卡顿与丢包。
2. **ChaCha20-Poly1305 算法适配**：对于基于 ARM Cortex-A53/A72 的路由器芯片（如友善 NanoPi、瑞芯微 RK3568），由于缺少专用 AES 模块，采用纯软件计算的 ChaCha20-Poly1305 算法效率通常优于 AES 加密，在选型节点底层加密算法时需针对性匹配。
3. **UDP 单边加速与并发多核调度**：基于 QUIC 协议构建的 Hysteria2 或 TUIC，由于在用户态维护单边拥塞控制算法，并发发包与丢包重传会对软路由的 Linux 内核软中断（softirq）带来巨大负担。若系统未开启 `Packet Steering`（RPS/RFS 多核分发）与硬件网络加速（Flow Offloading），千兆吞吐将直接被单核瓶颈掐死在 300Mbps 以内。

## 三、OpenWrt / iStoreOS 常见分流模式与网络架构全景对比

为了帮助大家理清 OpenClash、PassWall、SSR-Plus 等主流插件的底层工作机制，下表对常见架构分流模式进行了技术维度的结构化对比：

| 核心对比维度 | 主路由一体化模式 | 旁路由全局接管模式 | 旁路由单设备定向分流 | Tproxy 混杂透明代理 |
| :--- | :--- | :--- | :--- | :--- |
| **网络物理拓扑** | 软路由直连光猫拨号 | 主路由拨号，DHCP下发旁路由网关 | 主路由分发，仅指定终端改网关 | 基于 Linux iptables PREROUTING 规则 |
| **硬件算力要求** | 极高（双网口+强劲多核X86） | 中等（单千兆网口工控机即可） | 极低（低功耗 ARM 盒子皆可） | 中等（依赖内核 iptables 转发效率） |
| **国内直连损耗** | 零额外转发损耗，直接硬件卸载 | 数据包在内网多跳转一次（+0.5ms） | 仅受控设备有内网跳数损耗 | 需经过两次 NAT 查找，小包转发损耗约 3% |
| **DNS 防污染能力** | 依赖软路由自身 SmartDNS / MosDNS | 容易与主路由 DNS 发生递归死锁 | 隔离性好，受控终端独立解析 | 搭配 Fake-IP 模式可彻底杜绝污染 |
| **故障逃生难度** | 灾难级（软路由崩溃全家断网） | 需手动修改主路由 DHCP 网关指向 | 仅故障设备受影响，逃生极其简单 | 重启插件或刷新 iptables 即可回退 |
| **典型适用场景** | 极客独立单身公寓、小型工作室 | 影音爱好者、多智能终端普通家庭 | 游戏主机、外贸办公单台设备隔离 | 高并发、低延迟全流量精细化分流 |

## 四、旁路由全屋加速配置核心避坑指南

### 1. 规避内网流量“旁路兜圈”与双向 NAT 损耗
在 iStoreOS 与原生 OpenWrt 中，很多人直接在防火墙中开启 `动态伪装（MASQUERADE）`。这会导致终端设备访问内网 NAS 或国内网站时，源 IP 地址全部被篡改为旁路由 IP。不仅破坏了内网直连的单跳拓扑，更让 NAS 的访问日志失去客户端源溯源能力。  
**正确做法**：主路由必须保留静态路由表，在旁路由中关闭不必要的 WAN 口伪装，仅让境外流量在 mangle 表中打标并通过特定策略路由表出站。

### 2. 彻底拆解 DNS 劫持回环（DNS Loop）与 Fake-IP 冲突
家庭全屋加速最常遇到的故障是“国内网页打得开，但微信图片刷不出、应用商店打不开”。其核心原因在于**主路由与旁路由的 DNS 互相指向造成递归死环**。  
- 终端设备将 DNS 请求发送给旁路由；
- 旁路由的 Dnsmasq 未做分流，将国内请求回抛给主路由；
- 主路由的 DNS 转发又将请求重新扔回旁路由，最终导致 TTL 超时失效。  
**解决方案**：建议采用 Fake-IP（增强模式），将境内常见域名直接在上游配置通过 Alidns / 腾讯 DNSPod 进行直连解析，境外域名交由节点核心内部远端代理通道解析。

### 3. 主机游戏与影音设备的定向分流排障
智能家居设备（如米家网关、扫地机器人）频繁发生境外连通尝试，不仅浪费节点流量，更可能触发服务商的设备并发风控。必须在 OpenClash 或 PassWall 中设置“绕过特定客户端 MAC 地址”，让 IoT 设备彻底锁定国内网关直连。  
而对于家庭网络中的 PlayStation 5、Nintendo Switch 等游戏设备，如果直接走常规的网页代理节点，由于对称型 NAT（Symmetric NAT）的限制，会导致联机派对加入失败。具体主机游戏节点的 NAT 调优方案，请参考专门针对主机游戏网络的深度横评文章：[内部链接: Steam与主机联机游戏节点选型：NAT类型优化与丢包延迟排查](/wiki/routes/gaming-steam-ps5-switch-nat-nodes/)。

## 五、软路由与全屋加速常见问题 FAQ

### Q1：软路由千兆宽带为什么节点测速只能跑到 300Mbps？
**A:** 首先排查是否开启了 CPU 硬件网卡卸载（Software flow offloading / Hardware flow offloading）。如果使用的是带有虚拟化（PVE / ESXi）的软路由，必须将物理网卡驱动设置为“直通（PCIe Passthrough）”模式，避免 VirtIO 虚拟网卡的高频上下文切换损耗。其次，检查所选节点的底层加密协议是否与当前软路由 CPU 指令集匹配。

### Q2：开启旁路由后，手机微信经常出现“正在连接”或图片发不出去？
**A:** 这是典型的 MTU 跃点分片与 MSS 钳制错误。数据包经过软路由加密封装后体积增大，如果超过了物理主路由的 MTU 限制（PPPoE 默认为 1492），数据包将被强行切片或因开启了 DF（Don't Fragment）标志而被静默丢弃。在 OpenWrt 防火墙的常规设置中，勾选“MSS 钳制（MSS Clamping）”并重启防火墙即可完美解决。

### Q3：旁路由死机或插件崩溃，如何确保全屋智能家居不瘫痪？
**A:** 绝不要在主路由的全局 DHCP 中将默认网关直接改为旁路由 IP。推荐的架构是：主路由保持默认配置（网关指向主路由自身，DNS 为运营商或公共 DNS），仅在需要科学加速的设备（如 Apple TV、主力 PC）网络设置中手动修改静态网关为旁路由。这样即使旁路由断电维护，全屋基础网络与智能家居仍 100% 正常运行。
