# 全屋智能网关与透明代理分流实践：OpenClash/PassWall 混合部署与微信白名单避坑深度拆解

## Direct Answer（核心结论速览）

> [!IMPORTANT]
> **【核心结论 / Direct Answer】**
> 旁路网关通过主路由 DHCP 下发网关与 DNS 接管局域网流量。因单网口双向流量折返，易诱发微信图片转圈、AirDrop 失联与游戏主机 NAT 降级三大硬伤。标准破解法为：主路由负责硬件 NAT 转发，旁路由启用 TProxy 模式放行 LAN 源 IP，搭配 MosDNS 实施国内外零污染分流，针对微信与主机配置直连白名单，并引入 VRRP 双机热备根除单点断网。

## 一、 透明网关流量劫持机理与数据回环开销解析

旁路由（旁路网关）并非物理概念上的独立路由器，而是局域网内挂载的专用网络流量处理节点。其核心价值在于不改变主光猫拨号结构的前提下，接管局域网出海流量：

```
+-------------------------------------------------------------------------------+
|                       全屋双路由旁路透明代理流量拓扑图                            |
+-------------------------------------------------------------------------------+
[ 光纤接入 ] ---> [ 光猫 (桥接模式) ]
                       |
                       v (PPPoE 拨号 / 硬件 NAT 加速)
         +-----------------------------+
         | 主路由 (硬路由 192.168.1.1)  | <--- 负责全屋 Wi-Fi 覆盖与基础交换
         +-----------------------------+
             |                     ^
             | (1.客户端请求数据)     | (3.旁路由分流后，国内直连回传 WAN 发出)
             v                     |
+----------------------------------------------------+
| 旁路由 (OpenWrt / 软路由 192.168.1.2)                |
|   ├─ MosDNS: 区分国内外域名解析 (端口 5335)           |
|   ├─ TProxy 内核模块: 接管 TCP/UDP 并保留原始源 IP    |
|   └─ OpenClash: 规则引擎 (国内直连，海外加密出境)     |
+----------------------------------------------------+
             | (4.海外加密数据)
             v
[ 跨洋光缆至落地节点 ]
```

在常见的“单臂路由”模式下，所有内网流量均需在主路由交换芯片与旁路由单物理网口之间往返折返（Hairpin NAT）。这不仅造成局域网带宽翻倍占用，软路由 CPU 处理软中断（SoftIRQ）与 NAT 表项查询也极为密集。若配置粗放，将引发严重的网络拥塞与服务异常。

## 二、 全屋网络三大致命痛点深度攻坚与对策

家庭或工作室在部署旁路由后，最常遭遇的三大体验灾难及其底层破解方案如下：

### 1. 局域网设备发现与 AirDrop / 打印机失联
- **底层诱因**：旁路由防火墙若开启了全量伪装（MASQUERADE），会导致局域网内所有终端的源 IP 全被篡改为旁路由自身 IP，破坏了点对点识别；同时 mDNS 组播（`224.0.0.251:5353`）无法跨接口转发。
- **破解实操**：关闭防火墙全局 MASQUERADE，并在 OpenWrt 中安装配置 `avahi-daemon`，放行局域网组播流量。

### 2. 微信/企微图片视频加载转圈与“当前网络存在风险”
- **底层诱因**：微信长连接服务器 IP 被 Fake-IP 池接管，或部分 DNS 请求被送往境外 DoH 解析，导致连接到异地腾讯 CDN 边缘节点，直接触发腾讯账户防盗号风控机制。
- **破解实操**：在分流规则中将腾讯核心域名强制锁定国内 DNS，并在路由表添加直连白名单：

```yaml
# 微信与国内高敏服务防风控绕行白名单
rules:
  - DOMAIN-SUFFIX,weixin.qq.com,DIRECT
  - DOMAIN-SUFFIX,qpic.cn,DIRECT
  - DOMAIN-SUFFIX,qq.com,DIRECT
  - DOMAIN-KEYWORD,wechat,DIRECT
  - IP-CIDR,183.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,120.0.0.0/8,DIRECT,no-resolve
```

### 3. 主机游戏（PS5/Switch/Xbox）NAT 降级为 Strict/Type D
- **底层诱因**：透明代理核心的多重地址转换打乱了 UDP 端口对称性，导致 P2P 联机握手彻底失败。
- **破解实操**：不要让游戏主机走旁路由。在主路由中为游戏主机绑定静态 IP，DHCP 中将其默认网关与 DNS 直接指向主路由原生 IP（`192.168.1.1`），并在主路由开启 MiniUPnPd 实现全锥形 NAT。

## 三、 高性能 MosDNS + OpenClash 协同分流生产级架构

为了实现国内域名首包零污染、海外域名秒级响应，推荐采用“MosDNS 分流 + OpenClash 转发”架构：

```
+-------------------------------------------------------------------+
|                  MosDNS 智能分流与防污染处理流程                    |
+-------------------------------------------------------------------+
[ 客户端 DNS 请求 (53) ] ---> [ MosDNS 中枢 (5335) ]
                                    |
      +-----------------------------+-----------------------------+
      | (判断域名归属)                                             |
      v                                                           v
【中国大陆域名 (geosite:cn)】                               【海外域名 / 灰度域名】
      |                                                           |
      v                                                           v
[ 本地运营商 DNS / 阿里 223.5.5.5 ]                          [ 加密 DoH / 境外公共 DNS ]
      |                                                           |
      v (返回本地最优 CDN 真实 IP)                                   v (返回 Fake-IP / 代理解析)
[ 终端毫秒直连 ]                                             [ 交付 OpenClash 规则分流出境 ]
```

### OpenClash 防火墙自定义规则脚本实操
进入 OpenWrt 终端，在 `/etc/firewall.user` 添加针对性放行策略，避免流量无序死锁：

```bash
# 确保局域网互访不被代理核心劫持
iptables -t nat -I PREROUTING -d 192.168.0.0/16 -j ACCEPT
iptables -t mangle -I PREROUTING -d 192.168.0.0/16 -j ACCEPT

# 针对特定办公 PC 或游戏主机放行原生直连通道（绕过旁路核心）
iptables -t mangle -I PREROUTING -s 192.168.1.199 -j ACCEPT
```

## 四、 主旁路由 VRRP / Keepalived 双机热备高可用容灾

旁路由最大的系统痛点在于“单点故障”：一旦软路由崩溃或重启升级，全屋立即瘫痪断网，极易引发家庭矛盾。利用 **Keepalived（VRRP 协议）** 可构建秒级平滑容灾体系：

```
+-------------------------------------------------------------------------------+
|                       Keepalived VRRP 网关高可用容灾逻辑                         |
+-------------------------------------------------------------------------------+
[ 全屋局域网设备 ] ---> 默认指向虚拟网关 VIP: 192.168.1.254
                              |
       +----------------------+----------------------+
       | (主网关存活状态检测)                          | (心跳丢失时接管)
       v                                             v
【主状态 MASTER：旁路由 (192.168.1.2)】       【备份 BACKUP：主路由 (192.168.1.1)】
   状态: 正常分流，广播 VIP 承载流量             状态: 待机监听，硬件直连就绪
   若核心崩溃 / 关机维护 (3秒无响应) -----------> 自动接管 VIP，全屋无感回退直连
```

在旁路由部署 Keepalived 守护脚本，每隔 2 秒检测 OpenClash 进程。一旦代理进程异常或设备掉电，主路由在 3 秒内自动认领虚拟网关 IP `192.168.1.254`，全屋设备无需更改任何设置即刻恢复国内互联网通信。

## 六、 核心延伸 FAQ

### Q: 旁路由配置中，“网关互指”与“单向手动指定”有何本质区别？
**A:** “网关互指”（主路由 DHCP 下发旁路网关，旁路网关填主路由）属于**全局接管模式**，全屋所有设备无需手动设置，但容错率最低，旁路故障全屋断网；“单向手动指定”仅在需要出海的 PC 或电视端手动填写旁路网关，不污染智能家居与长辈设备，稳定性最高，是极客环境的首选方案。

### Q: OpenClash 的 TProxy 模式与 REDIR-HOST 模式在性能上有何差异？
**A:** REDIR-HOST 基于系统 NAT 转发，技术陈旧且易导致 UDP 关联失效，已被逐步淘汰；TProxy 模式基于 Linux 内核路由策略接管 TCP/UDP，能够完整保留数据包原始源 IP 与目标端口，对 QUIC、游戏加速及防 DNS 污染兼容性最好，但对软路由 CPU 性能略有要求。

### Q: 为什么接入旁路由后，国内千兆宽带测速上传速度明显缩水？
**A:** 主要受制于**单网口半双工流量折返**。当进行千兆极限压测时，数据在主路由与旁路由的单根千兆网线中同时上下行对冲，瞬间打满千兆物理带宽极限。解决方案是将旁路由升级为双 2.5G 网卡物理串接模式，或在分流规则中将测速服务器直接排除在旁路由之外。
