# 连通成功但网页打不开：三层金字塔排查系统代理、DNS 劫持与环回冲突

> [!IMPORTANT]
> **【Direct Answer / 30秒急救方案】**
> 如果客户端节点测速显示绿色延迟（如 80ms），但浏览器打开任何网页均提示 `ERR_PROXY_CONNECTION_FAILED` 或无限转圈，请按以下 **3 个最快生效动作** 执行急救：
> 1. **复位本地系统代理**：在客户端（如 Clash Verge Rev / v2rayN）中将「系统代理（System Proxy）」开关**关闭 3 秒后再重新打开**；若仍无效，按 `Win+R` 输入 `inetcpl.cpl` 进入连接 -> 局域网设置，取消勾选“为 LAN 使用代理服务器”。
> 2. **校准系统本地时钟**：打开 Windows 设置 -> 时间和语言 -> 日期和时间，点击「立即同步」。若本机与标准北京时间偏差超过 **90 秒**，TLS 1.3 握手时安全证书时间戳将被强制拒绝，引发全网断流。
> 3. **一键切换 TUN 虚拟网卡**：关闭浏览器第三方代理插件（如 SwitchyOmega），在客户端启用 **TUN 模式（虚拟网卡接管）**，绕过脆弱的本地 HTTP 系统代理端口直接进行三层网络接管。

## 01 故障现象对照：你是哪一种“伪连通”？

“节点测速通了”是许多网络新手最大的认知误区。客户端面板显示的 `120ms`，通常仅代表**从你的本地客户端向服务商入口服务器发起单次 TCP 握手或 ICMP Ping 的耗时**，完全不代表真实的端到端网络数据传输已经打通。

请先核对下表，精准锁定你当前的故障层级与排查切入点：

| 故障现象表象 | 终端 / 浏览器报错代码 | 根本原因定位 | 关键修复方向 |
| :--- | :--- | :--- | :--- |
| **百度打得开，Google 永远打不开** | `ERR_TIMED_OUT` / `DNS_PROBE_FINISHED_NXDOMAIN` | 分流规则未接管海外域名、Fake-IP 路由未下发、节点出口被墙 | 检查分流模式是否误设为 Direct；更新本地规则集；更换可用节点 |
| **所有网页全断，百度也无法访问** | `ERR_PROXY_CONNECTION_FAILED` | 本地系统代理端口被劫持或内核异常崩溃但注册表代理未释放 | 复位注册表 ProxyEnable；重启客户端核心进程；一键清理端口占用 |
| **浏览器正常，Git / 终端 / 游戏全断** | `Failed to connect to github.com port 443` | 普通系统代理仅作用于遵循 HTTP 环境变量的应用，非系统全局 | 开启 TUN 模式虚拟网卡或手动为终端注入 `http_proxy` 环境变量 |
| **Windows 应用商店 / 局域网无法联网** | `UWP Loopback Blocked` / 错误代码 `0x80072EFD` | 微软沙盒机制禁止 UWP 应用访问本机 `127.0.0.1` 回环代理 | 运行 `CheckNetIsolation` 解除 Windows 沙盒回环网络隔离 |
| **测速瞬间有绿字，网页打开发送后断流** | `ERR_CONNECTION_RESET` / TLS 握手卡死 | 本机时间偏差导致证书失效；或节点遭遇晚高峰严重超售 QoS 熔断 | 强制同步 NTP 时钟；如果持续发生，说明节点已被严重超售限速 |

## 02 三层金字塔排查法：从本地到远端的系统级诊断

网络排障绝不能“病急乱投医”。我们提出**网络分流排查三层金字塔模型**：先排除最基层的本地协议栈与系统代理死锁，再排查中层的虚拟网卡与 DNS 路由，最后排查顶层的节点出口与链路质量。

```text
                  ▲
                 / \\
                /顶层\\   【第三层：远程出口与链路】（节点阻断、晚高峰超售、商户跑路）
               /------\\
              /  中层  \\  【第二层：DNS 与虚拟网卡】（Fake-IP 污染、Wintun 驱动、跃点）
             /----------\\
            /    基层    \\ 【第一层：本地系统与代理】（注册表死锁、系统时钟、端口冲突）
           /--------------\\
```

---

### 第一层排查：本地系统代理、端口冲突与时钟偏差

这是 85% 以上“连上但打不开网页”的病灶所在。

#### 1. 系统代理注册表死锁与残留
当客户端异常退出、死机或强制关机时，写入 Windows 注册表的代理开关未被正常还原，导致系统仍然把流量发往已经不存在的本地端口（如 `127.0.0.1:7890`）。

**排查与一键修复（PowerShell 管理员模式）**：
```powershell
# 1. 查询当前 Windows 系统代理配置
Get-ItemProperty -Path 'HKCU:\\Software\\Microsoft\\Windows\\CurrentVersion\\Internet Settings' | Select-Object ProxyEnable, ProxyServer

# 2. 若 ProxyEnable 为 1 但客户端未启动，运行以下命令一键清除代理死锁
Set-ItemProperty -Path 'HKCU:\\Software\\Microsoft\\Windows\\CurrentVersion\\Internet Settings' -Name ProxyEnable -Value 0
```

#### 2. 本地端口占用冲突（7890 / 7897 端口冲突）
若你同时安装了多个代理软件（例如同时开启了 Clash 与 v2rayN，或者后台残留了未杀死的旧核心进程），会导致新客户端监听端口失败，控制台日志出现 `bind: address already in use`。

```powershell
# 查询 7890 端口被哪个 PID 占用
netstat -ano | findstr :7890

# 强制结束冲突进程（将 <PID> 替换为实际数字）
taskkill /F /PID <PID>
```

#### 3. 系统时间偏移与 TLS 1.3 证书熔断
现代安全代理协议（如 VLESS Reality、Trojan、Shadowsocks-AEAD）均重度依赖时间戳鉴权。如果你的电脑主板电池老化、或者系统长期未联网校准时间，一旦与 UTC 标准时间误差超过 **90 秒**，客户端向节点发起的握手包会被服务端判定为“重放攻击”直接丢弃；浏览器也会因 SSL 证书尚未生效或过期而彻底断开。

> [!TIP]
> 进入 Windows「设置」->「时间和语言」->「日期和时间」，确保开启「自动设置时间」，并点击**「立即同步」**按钮，直到看到对勾提示。

### 第二层排查：DNS 污染、Fake-IP 路由黑洞与 TUN 驱动故障

当第一层排查无误，但仍然无法解析域名或打开网页时，问题往往出在域名解析（DNS）与三层虚拟网卡路由上。

#### 1. Fake-IP 模式解析冲突与黑洞
大多数现代客户端（如 Clash Verge Rev、Sing-Box）默认启用 `fake-ip` 模式。客户端内置 DNS 会为请求分配一个保留私有 IP 地址段（如 `198.18.0.0/16`），并由内核在出站时进行反查映射。

- **问题根源**：如果本地浏览器开启了安全 DNS（DoH，如 Chrome 的「使用安全 DNS」），浏览器会直接绕过本地客户端的 DNS 模块，将加密解析请求送至公共 DNS 服务器。这导致客户端无法捕获真实的域名映射，数据包流入 Fake-IP 黑洞。
- **解决方案**：
  1. 打开 Chrome / Edge 设置，搜索「安全 DNS」，**将其彻底关闭**，交给本地代理客户端统筹调度。
  2. 若仍有异常，在客户端设置中将 DNS 模式由 `fake-ip` 临时切换为 `redir-host` 进行交叉排查。

#### 2. Wintun 虚拟网卡驱动崩溃与多网卡跃点优先级
在开启 TUN 模式后，客户端会在系统中生成一个名为 `wintun` 或 `Mihomo` 的虚拟网卡。

```powershell
# 检查网络适配器中虚拟网卡状态
Get-NetAdapter | Where-Object { $_.InterfaceDescription -match "Wintun|Clash" }
```

若物理网卡跃点数（Metric）小于虚拟网卡跃点数，Windows 数据包仍会优先走未加密的物理出口，引发断网。详细的虚拟网卡修复流程可参考本站同系列专文：[TUN 虚拟网卡模式启动断网与驱动冲突排查](/troubleshooting/tun-failure/)。

### 第三层排查：远程服务节点、线路超售与目标网站风控

如果你已经完成上述两层排查，本地直连访问国内网站完全通畅，但海外流量依然全部超时，病根则出在**服务商服务端或国际公网链路**。

#### 1. 节点被墙或国内中转入口被封
服务商的国内前置 BGP 入口或海外落地机房 IP 遭到运营商 SNI 拦截或黑洞清洗。在客户端进行批量测试时，节点延迟全部变成红色超时（Timeout）。
- **验证手段**：切换手机 4G/5G 热点测试。若手机热点可用而家庭 Wi-Fi 不可用，说明你本地光猫宽带的运营商出口发生了路由阻断。
- **防范机制**：若服务商频繁出现大面积超时失联，说明其缺乏多入口容灾冗余。请严格执行 [新手选购 8 大避坑法则](/buying/traps/)，切勿被不良商家的年付廉价套餐套牢。

#### 2. 晚高峰严重超售与丢包熔断
许多劣质廉价中转商在晚间 20:00 - 23:00 黄金时段将 1Gbps 的带宽超售卖给数千人使用。虽然 ICMP Ping 包依然能正常回包显示“绿字”，但一旦浏览器发起高并发 HTTP/2 握手，瞬间丢包率飙升至 40% 以上，触发 TCP 拥塞控制熔断，导致网页长时间转圈打不开。
- **终极解决方案**：若你的使用场景包含跨国远程会议、外贸办公或海外生产力，建议升级至具备物理物理隔离的 [晚高峰抗封锁专线评测榜（IPLC/IEPL）](/rankings/iplc-iepl/)。

#### 3. 目标网站 IP 封锁与 Cloudflare 1020 阻断
如果你打得开 Google 和 YouTube，但唯独打不开 ChatGPT 或 Claude，提示 `Access Denied 403` 或 `Error 1020`，这并非网络故障，而是当前节点 IP 被 Cloudflare 风控列入高危机房黑名单。
- **应对方案**：查阅 [AI 生产力节点推荐榜单](/rankings/ai-services/)，切换为经过 IPinfo 认证的纯血双 ISP 家庭住宅原生 IP。

## 03 系统级排障操作大表（命令与图形化对照）

遇到故障时，按照下表依序在操作系统中执行排错，绝大多数“断流无网”问题均可在 3 分钟内彻底解决：

| 步骤 | 排查层级 | 操作目标 | 具体执行指令 / 图形化路径 | 预期成功结果 |
| :---: | :--- | :--- | :--- | :--- |
| **Step 1** | 本地基础网络 | 验证家庭光猫与 Wi-Fi 是否通畅 | 浏览器无痕模式打开 `https://www.baidu.com` | 国内网站秒级打开，证明物理网卡与光纤正常 |
| **Step 2** | 系统代理开关 | 释放死锁的 Windows 代理端口 | `Win+R` -> `inetcpl.cpl` -> 连接 -> 局域网设置 -> 清空代理设置 | 取消勾选“为 LAN 使用代理服务器”并保存 |
| **Step 3** | 网络协议栈重置 | 修复 Winsock 目录与 IP 堆栈损坏 | 管理员身份运行 CMD：<br>`netsh winsock reset`<br>`netsh int ip reset` | 提示“成功重置 Winsock 目录”，重启电脑生效 |
| **Step 4** | DNS 缓存刷新 | 清理被污染或失效的旧解析记录 | 运行 CMD：<br>`ipconfig /flushdns` | 显示“已成功刷新 DNS 解析缓存” |
| **Step 5** | 本地环回隔离 | 解决 Windows 10/11 应用商店与 UWP 无法联网 | 管理员身份运行 PowerShell：<br>`CheckNetIsolation.exe LoopbackExempt -a -n=<PackageFamilyName>` | UWP 应用解除沙盒限制，可正常通过 127.0.0.1 上网 |
| **Step 6** | 客户端内核诊断 | 排查分流规则与连接明细 | 打开 Clash / Sing-Box 的「Connections（连接）」与「Logs（日志）」标签页 | 查看目标请求是否触发了 `REJECT` 规则或报证书错误 |

## 04 常见错误场景与深度解答 (FAQ)

### Q1：为什么微信、QQ 能收发文字，但浏览器所有网页都打不开？
> **Direct Answer**：这是经典的 **DNS 故障或 80/443 网页端口受阻** 现象。
> 微信与 QQ 等即时通讯工具内置了内置 IP 直连列表（不依赖系统 DNS 解析即可登录并收发文本数据）。而浏览器访问网页必须先经过 DNS 将域名解析为 IP，再通过 TCP 80/443 端口发起 HTTP/HTTPS 握手。
> 当你的系统代理崩溃或本地 DNS 出现故障时，浏览器无法解析任何域名，而微信仍然可以在直连 IP 缓存下保持在线。解决办法是：按上述 Step 2 彻底检查系统代理开关，并在网络适配器中将 IPv4 的 DNS 更改为 `223.5.5.5` 或 `119.29.29.29`。

### Q2：我开了“全局（Global）”模式，为什么还是打不开海外网站？
> **Direct Answer**：许多人误以为“全局模式就是万能解药”。事实上，**全局模式仅代表强行让所有流量走同一个节点，完全不代表节点本身是通畅的**！
> 如果你选中的那个落地节点本身服务器宕机、IP 被墙、或者你的套餐流量已经用尽，切换为全局模式只会让你的电脑从“部分打不开”变成“彻底断网”。日常使用建议永远保持 **Rule（规则分流）模式**，并前往客户端节点列表执行测速，挑一个延迟在 150ms 以内的绿色可用节点再试。

### Q3：为什么切换不同 Wi-Fi 或连手机热点就能正常上网？
> **Direct Answer**：这证明问题**百分之百出在你原来那个 Wi-Fi 路由器的网络策略或光猫 DNS 拦截上**。
> 部分公司企业内网、校园网或家庭智能路由器开启了「家长控制」或「恶意端口防护」，直接从交换机层面屏蔽了 `UDP 443（QUIC）`、`Shadowsocks 常用端口`，或者强行劫持了所有指向外部的 53 端口 DNS 请求。
> 解决办法是：在代理客户端中开启 **TUN 模式**，并将分流协议切换为基于 TCP 伪装的 Reality 或 WebSocket 协议；如果属于恶劣网络环境，查阅 [主流代理协议选型指南](/kb/concepts/protocols-explained) 了解更多抗封锁特性。

## 05 进阶建议与长效稳定方案

如果经过上述全流程诊断，排查出故障是由于节点线路频繁超时、晚高峰带宽卡死或服务商入口经常失联所致，说明你目前使用的网络服务质量已经无法满足日常需求。持续在劣质节点上浪费时间排错并不可取，建议按以下指引重构你的科学网络体系：

1. **避免单点故障**：日常电脑中至少保留两家独立服务商的订阅，实现双链路互备；
2. **严防年付陷阱**：坚守小额月付原则，参阅 [2026 稳定节点综合推荐榜](/rankings/best/) 选型经过晚高峰压测验证的服务；
3. **深入底层排障**：更多具体客户端与网络环境排障技术，欢迎继续查阅本站 [故障排查全景索引页](/troubleshooting/) 与 [网络分流急救综合手册](/troubleshooting/guide/)。
